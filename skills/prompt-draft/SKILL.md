# Prompt Draft Skill

## 技能说明

此技能用于为任务委派起草高质量的提示词，确保子任务能够被准确执行。

## 适用场景

- 需要委派任务给其他 AI 代理
- 需要生成详细的实现指南
- 需要确保任务执行的一致性
- 复杂任务需要明确的执行步骤

## 提示词结构

### 标准模板

```markdown
# 任务：[任务名称]

## 1. 任务目标
[一句话描述要达成什么]

## 2. 预期产出
[具体的交付物，如文件、代码、文档等]

## 3. 必须使用的工具
[明确列出允许使用的工具，防止工具滥用]
- 工具1：用途
- 工具2：用途

## 4. 必须遵守的规则
[明确的约束条件]
- 规则1
- 规则2
- 规则3

## 5. 禁止的行为
[明确禁止的操作，防止越界]
- 禁止1
- 禁止2
- 禁止3

## 6. 上下文信息
[执行任务所需的背景信息]
- 相关文件路径
- 现有代码模式
- 依赖关系
- 配置信息

## 7. 实现步骤（可选）
[如果需要明确步骤]
1. 步骤1
2. 步骤2
3. 步骤3

## 8. 验证要求
[如何验证任务完成]
- 验证点1
- 验证点2
- 验证点3
```

## 提示词质量标准

### 1. 明确性
- ✅ 目标清晰，不含糊
- ✅ 范围明确，不超界
- ✅ 产出具体，可验证

### 2. 完整性
- ✅ 包含所有必要信息
- ✅ 提供足够的上下文
- ✅ 列出所有约束条件

### 3. 可执行性
- ✅ 步骤可操作
- ✅ 工具可用
- ✅ 验证可行

### 4. 防御性
- ✅ 明确禁止事项
- ✅ 限制工具使用
- ✅ 防止范围蔓延

## 示例

### 示例 1：实现 CLI 命令

```markdown
# 任务：实现 clawkit init 命令

## 1. 任务目标
实现项目初始化命令，生成默认配置文件

## 2. 预期产出
- packages/cli/src/commands/init.ts
- 更新 packages/cli/src/index.ts 注册命令

## 3. 必须使用的工具
- write：创建新文件
- edit：修改现有文件
- read：读取现有代码
- lsp_diagnostics：检查类型错误

## 4. 必须遵守的规则
- 使用 TypeScript 严格模式
- 所有注释使用中文
- 函数必须有返回类型
- 错误信息使用中文
- 遵循现有代码风格

## 5. 禁止的行为
- 禁止使用 any 类型
- 禁止引入新的依赖（除非讨论）
- 禁止修改其他不相关文件
- 禁止实现超出范围的功能

## 6. 上下文信息
- CLI 入口：packages/cli/src/index.ts
- 共享类型：packages/shared/src/index.ts
- 配置模板：examples/all-in-one.yaml
- 当前阶段：项目初始化，只实现基础功能

## 7. 实现步骤
1. 创建 packages/cli/src/commands/init.ts
2. 实现 init 函数：
   - 检查当前目录是否已有配置文件
   - 询问用户选择部署模式
   - 根据模式复制对应的模板文件
   - 输出成功信息
3. 在 packages/cli/src/index.ts 中注册命令
4. 运行 lsp_diagnostics 检查类型错误
5. 测试命令是否可用

## 8. 验证要求
- 执行 pnpm build 成功
- 无 TypeScript 类型错误
- 可以执行 clawkit init 命令
- 生成的配置文件格式正确
```

### 示例 2：修复 Bug

```markdown
# 任务：修复构建失败问题

## 1. 任务目标
修复 packages/controller 的类型错误

## 2. 预期产出
- 修复后的代码
- 构建成功的验证

## 3. 必须使用的工具
- read：读取错误文件
- lsp_diagnostics：查看类型错误
- edit：修复代码
- bash：运行构建验证

## 4. 必须遵守的规则
- 只修复类型错误，不重构代码
- 保持现有代码结构
- 不改变公共 API

## 5. 禁止的行为
- 禁止使用 any 或 @ts-ignore 绕过错误
- 禁止删除类型定义
- 禁止修改不相关的代码

## 6. 上下文信息
- 错误文件：packages/controller/src/index.ts
- 共享类型：packages/shared/src/index.ts
- 错误信息：[具体错误信息]

## 7. 实现步骤
1. 读取错误文件
2. 运行 lsp_diagnostics 查看详细错误
3. 分析错误原因
4. 修复类型错误
5. 再次运行 lsp_diagnostics 确认修复
6. 运行 pnpm build 验证

## 8. 验证要求
- lsp_diagnostics 无错误
- pnpm build 成功
- 所有类型定义正确
```

## 提示词反模式

### ❌ 模糊的目标
```markdown
# 任务：改进 CLI
```
**问题**：目标不明确，范围不清晰

### ❌ 缺少约束
```markdown
# 任务：实现配置解析
实现一个配置解析功能
```
**问题**：没有规则和禁止事项，容易越界

### ❌ 缺少上下文
```markdown
# 任务：修复 bug
修复 controller 的 bug
```
**问题**：没有提供错误信息和相关文件

### ❌ 步骤过于详细
```markdown
# 任务：添加函数
1. 打开文件
2. 找到第 10 行
3. 在第 10 行后插入...
4. 保存文件
```
**问题**：过度指导，限制了执行灵活性

## 使用指南

### 何时使用此技能

- ✅ 委派复杂任务
- ✅ 需要确保执行质量
- ✅ 任务有明确的约束
- ✅ 需要防止范围蔓延

### 何时不使用此技能

- ❌ 简单的一步操作
- ❌ 探索性任务
- ❌ 需要高度灵活性的任务

## 提示词优化技巧

### 1. 使用具体的动词
- ✅ "创建 init.ts 文件"
- ❌ "处理初始化"

### 2. 量化产出
- ✅ "生成 3 个配置文件"
- ❌ "生成一些配置"

### 3. 明确边界
- ✅ "只修改 packages/cli，不要改其他包"
- ❌ "修改 CLI"

### 4. 提供示例
- ✅ "错误信息格式：`部署失败：${reason}`"
- ❌ "输出错误信息"

### 5. 分层约束
- 必须做：核心要求
- 应该做：最佳实践
- 禁止做：明确边界

## 与其他技能的配合

- **task-intake** → **prompt-draft**：任务明确后起草提示
- **prompt-draft** → **dispatch-check**：检查是否应该委派
- **prompt-draft** → 执行：使用提示词执行任务

## 注意事项

1. 提示词要详细但不啰嗦
2. 约束要明确但不僵化
3. 步骤要清晰但不过度指导
4. 上下文要充分但不冗余
5. 验证要具体但不繁琐
