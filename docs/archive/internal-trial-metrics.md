# 内部试运行观察指标

## 使用原则

- 本文用于定义 **clawkit v0.1.0 内部试运行期间的人工观察指标**。
- 当前阶段不引入复杂监控系统，以“人工记录 + 命令输出 + 页面观察 + 日志定位”为主。
- 记录目标不是做漂亮报表，而是帮助判断：当前版本是否适合扩大试运行范围，哪些问题应优先进入 v0.1.1 修复清单。

## 建议记录方式

建议使用一张简单表格或试运行日志，按“场景 / 时间 / 结果 / 备注”记录。例如：

| 日期 | 场景 | 指标 | 结果 | 证据 | 备注 |
|---|---|---|---|---|---|
| 2026-03-13 | 单机场景 | 任务创建成功率 | 4/5 | taskId 列表、截图、日志路径 | 1 次因 token 配置错误失败 |

建议同时保留以下证据：

- taskId / dispatchId
- 页面截图
- API 响应摘要
- controller / worker / OpenCode 日志路径
- 实际执行命令

## 一、功能类指标

### 1. 任务创建成功率

- 指标定义：成功创建任务的次数 / 尝试创建任务的总次数
- 观察对象：API 创建任务、OpenClaw webhook 创建任务、页面创建后任务是否可见
- 建议记录方式：记录每次创建的来源、taskId、是否生成 `taskDraft`
- 判定说明：
  - 高：绝大多数请求都能成功创建任务，失败可归因于输入问题
  - 低：经常出现无法创建、静默失败、创建后查不到任务

### 2. 草稿生成成功率

- 指标定义：成功生成 `promptDraft` 的次数 / 任务创建成功次数
- 观察对象：任务创建后是否能看到草稿摘要和版本信息
- 建议记录方式：记录 taskId、草稿版本、生成耗时大概范围
- 判定说明：若频繁出现任务已创建但无草稿，说明主链路前段存在问题

### 3. 草稿确认成功率

- 指标定义：成功完成人工确认派发的次数 / 尝试确认次数
- 观察对象：`POST /api/approval/:taskId/approve`、页面确认派发按钮、OpenClaw 文本协议确认
- 建议记录方式：记录确认入口、操作人、最终状态变化
- 判定说明：若确认后状态无变化、重复确认、页面提示不清晰，应记为失败或异常

### 4. 任务执行成功率

- 指标定义：最终进入 `done` 的任务数 / 已派发任务总数
- 观察对象：worker 执行日志、任务状态页、执行摘要
- 建议记录方式：按 taskId 记录最终状态、是否走 placeholder fallback、是否真实 OpenCode 执行
- 判定说明：必须把“链路打通成功”和“真实 OpenCode 执行成功”分开记录，避免混淆

### 5. 结果回传成功率

- 指标定义：worker 完成后成功回传 controller 并可被查询到的次数 / 执行结束次数
- 观察对象：result 提交日志、状态 API、任务详情页执行摘要
- 建议记录方式：记录 taskId、结束状态、是否能在页面和 API 同时看到结果
- 判定说明：若 worker 本地显示完成，但 controller 无结果，应视为关键异常

## 二、部署类指标

### 1. apply 成功率

- 指标定义：按预期完成 dry-run 或真实写入的次数 / apply 尝试次数
- 观察对象：CLI 输出、生成文件、备份文件、页面 Deploy 操作结果
- 建议记录方式：分别记录 dry-run 和真实执行结果，标注使用的 manifest 和拓扑
- 判定说明：若输出显示成功但文件未生成、备份缺失或路径错误，应视为失败

### 2. heal 修复成功率

- 指标定义：heal 在能力范围内成功修复问题的次数 / 进入自动修复的问题次数
- 观察对象：`heal --dry-run` 识别结果、`heal --force` 修复结果
- 建议记录方式：记录问题类型、是否属于可自动修复、修复后复检结果
- 判定说明：只统计当前支持的问题类型，不把本就不支持自动修复的问题算成失败

### 3. doctor 误报 / 漏报

- 指标定义：
  - 误报：doctor 报错但实际无问题
  - 漏报：实际有问题但 doctor 未识别
- 观察对象：manifest 校验、路径检查、端口冲突、环境检查、节点结构检查
- 建议记录方式：逐条记录“doctor 结论 vs 实际情况”
- 判定说明：doctor 当前主要做配置与结构检查，不应按未来网络探测能力要求它；但对当前已实现项的误报/漏报要重点记录

## 三、页面类指标

### 1. 页面可访问性

- 指标定义：总览 / 配置 / 部署 / 修复 / 状态 / 任务中心页面可正常打开的比例
- 观察对象：页面加载、路由跳转、生产托管下的 SPA fallback
- 建议记录方式：记录每个页面是否能打开、是否出现白屏或 404
- 判定说明：若页面必须频繁刷新、重启或改用 API 才能继续，说明可访问性不足

### 2. 页面操作完成率

- 指标定义：页面内关键操作可直接完成的比例
- 观察对象：保存 manifest、执行 doctor / plan / apply / heal、查看任务详情、确认派发、修改草稿
- 建议记录方式：按操作项记录“成功 / 失败 / 需要 CLI 补救”
- 判定说明：若核心操作经常需要切回 CLI 才能完成，应记为体验不足

### 3. API 报错情况

- 指标定义：页面操作引发 API 报错的次数、类型与可定位程度
- 观察对象：浏览器页面提示、接口响应 message/code/details
- 建议记录方式：记录接口路径、错误码、错误文案、触发步骤
- 判定说明：报错本身不一定是坏事，关键是是否结构化、是否能指导排查

### 4. 前端错误提示质量

- 指标定义：前端错误提示是否足够让内部试运行人员理解并采取下一步动作
- 观察对象：页面 toast、错误块、空状态、失败提示文案
- 建议记录方式：对每次失败操作给 3 档评价：清晰 / 基本可懂 / 难以理解
- 判定说明：若只能靠开发人员读控制台才能理解问题，应判为质量偏低

## 四、稳定性类指标

### 1. controller 崩溃情况

- 指标定义：试运行期间 controller 异常退出次数、触发条件、恢复难度
- 观察对象：进程退出、接口全不可用、日志异常中断
- 建议记录方式：记录退出时间、触发操作、恢复方式
- 判定说明：主控制面异常退出属于高优先级问题

### 2. worker 掉线情况

- 指标定义：worker 失联、长时间不心跳、任务执行中掉线的次数
- 观察对象：状态页、worker 注册列表、pull / heartbeat 日志
- 建议记录方式：记录 workerId、掉线时长、对任务的影响
- 判定说明：偶发掉线可记录为稳定性问题；若导致任务卡死，应升级为阻塞问题

### 3. OpenCode serve 异常情况

- 指标定义：OpenCode server 启动失败、不可达、认证失败、执行链路中断的次数
- 观察对象：worker 错误摘要、OpenCode 日志、执行失败信息
- 建议记录方式：记录是否为真实执行验证场景、错误类型、是否可恢复
- 判定说明：应与 placeholder fallback 场景区分，避免误判真实执行能力

### 4. 任务卡死情况

- 指标定义：任务长时间停留在非最终状态的次数
- 观察对象：`waiting_approval / approved / dispatched / running` 状态停留时间
- 建议记录方式：记录 taskId、停留阶段、持续时间、最后处理方式
- 判定说明：卡死比直接失败更需要优先处理，因为会影响试运行判断

### 5. 状态不一致情况

- 指标定义：页面、API、日志三者之间状态描述不一致的次数
- 观察对象：任务状态、worker 状态、最新 doctor / apply / heal 结果
- 建议记录方式：记录不一致项、来源、时间点
- 判定说明：若状态无法互相印证，会直接降低内部试运行可信度

## 五、体验类指标

### 1. 文档可跟随性

- 指标定义：执行人能否按 README、最小使用手册、试运行文档顺利完成操作
- 观察对象：是否需要频繁请教开发者、是否存在步骤跳跃或遗漏
- 建议记录方式：记录“可直接照做 / 需要口头补充 / 基本无法照做”
- 判定说明：若内部试运行严重依赖作者口头解释，说明文档还不够可用

### 2. 错误提示易理解程度

- 指标定义：非实现人员是否能从 CLI / API / 页面提示中理解问题方向
- 观察对象：中文提示、建议动作、日志定位信息
- 建议记录方式：问题发生后，让执行人用一句话复述“他理解的问题是什么”
- 判定说明：若复述内容与真实问题偏差很大，说明提示质量不足

### 3. 首次部署顺畅度

- 指标定义：第一次按文档从零开始完成 build、doctor、apply、启动服务的难易程度
- 观察对象：是否存在阻塞步骤、隐含前提、不可预期的人工补动作
- 建议记录方式：记录首次从开始到跑通所需时间，以及卡住点
- 判定说明：当前版本允许存在人工步骤，但不应存在“文档未提及的关键步骤”

### 4. 页面是否足够支撑日常使用

- 指标定义：内部试运行期间，Web Console 是否足以承担日常查看、确认、状态回查与基础运维
- 观察对象：是否仍频繁需要改用 CLI 或手工查日志
- 建议记录方式：记录每天主要操作中，有多少比例可在页面内完成
- 判定说明：当前目标不是做复杂后台，但至少应支撑最小日常使用

---

## 试运行判定建议

可按以下方式做人工结论：

1. **主链路是否稳定**：功能类与稳定性类是否支持内部日常试运行
2. **部署与修复是否够用**：doctor / apply / heal 是否足以支撑内部问题排查
3. **页面是否够用**：Web Console 是否能承担最小可视化入口角色
4. **文档是否够跟随**：执行人是否能按文档独立完成主要动作

若以上四项中有两项及以上明显不足，应优先进入 v0.1.1 修复，而不是扩大试运行范围。
